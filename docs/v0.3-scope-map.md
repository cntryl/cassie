# v0.3 Issue-to-Contract Map

This map translates the GitHub membership of milestone #7,
“v0.3 Projection store,” into the release boundaries in the
[Product Roadmap](product-roadmap.md). It is a snapshot from `main` at
`f5ecd5f922e917d5742094323601ffedbaa6ec8d`, read on 2026-10-20. GitHub reported
30 assigned issues: 23 open and 7 closed.

The current roadmap is the product authority. Existing milestone assignment,
issue label, and older text inside an issue do not expand that scope. In
particular, the closed #791–#793 full-PostgreSQL parity program and its copied
acceptance text are superseded by the current roadmap's finite read-model
contract and permanent exclusions.

The classifications began as review dispositions. On 2026-10-21, after the
user authorized a minimum issue update, #777 was scoped to the selected v0.3
catalog/session/client workflow and unblocked from v0.4 #762; #842 was scoped
to selected scalar-index lifecycle and unblocked from v1.0 #768. No issue was
created, closed, or reassigned at that time. The gate and issue states have
since changed; see the live refresh at the end of this map.

## Current Roadmap Owners

- **v0.3 Projection Store:** projection writes and replay, read-model lifecycle
  and rebuild, and the selected pgwire, driver, ORM, migration-tool, and admin
  workflows named by the contract.
- **v0.4 Query and retrieval:** selected read/query behavior, types, functions,
  operators, and full-text, vector, and hybrid retrieval.
- **v1.0 Production release:** representative-scale performance, concurrency,
  recovery, operational thresholds, and release evidence.
- **Cross-cutting:** repository CI and test-fixture maintenance that does not
  define one of those product acceptance surfaces.

Every v0.3 behavior remains bounded by the named workflow and issue criterion.
This map does not select full PostgreSQL parity, stored programs, distributed
coordination, or a second storage layer. Midge remains the only storage layer.
Each database's catalog and rows share its physical family; cross-database
transactions remain unsupported, and current replay/lifecycle paths may still
use multiple transactions within one family.

### 2026-10-29 — #842 partial-index restart witness

`should_recover_partial_index_entries_after_committed_writes_on_restart` adds
disk-backed evidence for partial covering-index entry persistence after
committed predicate-changing writes. After restart, the eligible query still
selects the index and returns the same rows as an independent scan. This is one
restart witness; the broader #842 index-shape and lifecycle acceptance remains
open.

### 2026-10-29 — #842 expression-index rollback witness

`should_preserve_expression_index_scan_equivalence_through_transaction_resolution`
creates a `lower(email)` index over populated rows and compares selected-index
reads to a separate unindexed table. It checks rekey, insert and delete inside
the transaction, after rollback, and after commit. EXPLAIN identifies the index
and confirms the comparison scan before the transaction and after rollback and
commit; it does not prove index selection while writes are staged. This witness does
not complete broader #842 index-shape or lifecycle acceptance.

### 2026-10-29 — #842 expression-index restart witness

`should_recover_expression_index_after_committed_rekey` creates a
`lower(email)` index over populated rows, commits an indexed-key update plus
insert and delete changes, then restarts local storage. The hydrated index
remains selected for the matching expression query, and its rows match an
independent scan after dropping the index. This is a test-only qualification
witness on the candidate branch; broader #842 acceptance remains open.

### 2026-10-29 — #842 partial-index schema-move witness

`should_preserve_partial_covering_index_across_table_schema_move` covers a
partial covering btree index when its owning table moves schemas. The index
remains selected after the committed move, the catalog reports its target
schema, a target-qualified `DROP INDEX` removes it, the unique index continues
rejecting duplicate keys, and the resulting scan matches the indexed rows.
Transaction rollback restores the source table, index, and unique enforcement.
`should_preserve_moved_index_identity_after_local_restart`,
`should_enforce_moved_unique_index_after_local_restart`, and
`should_drop_moved_index_by_target_qualified_name_after_local_restart` verify
the index OID, duplicate rejection, and qualified drop after local-storage
restart.
This also fixed a catalog-name mismatch that made the moved index appear in
`pg_indexes` and query plans but fail schema-qualified lookup. Broader #842
index-shape and lifecycle acceptance remains open.

### 2026-10-29 — #833 v0.3 transactional-DDL boundary reconciled

The live wire contract, implementation whitelist, and tests establish the
selected v0.3 same-family transactional-DDL runtime. The implicit Query/Sync
path keeps other catalog DDL standalone and rejects mixed Simple Queries
before execution. No additional selected v0.3 runtime gap was identified in

### 2026-10-29 — #839 DROP COLUMN CASCADE recovery witness

`should_restore_dropped_column_dependencies_after_transaction_rollback`
verifies that rollback restores a dropped referenced column, its dependent view
and foreign key, including referential-integrity enforcement.
`should_recover_column_cascade_dependency_removal_after_local_restart`
verifies that a committed cascade keeps those dependencies removed after local
restart while retaining unrelated parent data. This CASCADE increment did not
qualify column-level `RESTRICT`; see the following note for that separate
SQLSTATE correction. These are coverage additions for an existing runtime path;
broader #839 acceptance remains open.

### 2026-10-29 — #839 column RESTRICT SQLSTATE parity

PostgreSQL 18.6 returns SQLSTATE `2BP01` and leaves a column and its dependent
foreign key/view intact when `DROP COLUMN ... RESTRICT` is rejected. The
focused Cassie probe reproduced a mismatch: the foreign-key path returned
`22000`. It now uses the typed dependency diagnostic and is covered by
`should_reject_drop_column_restrict_without_mutating_dependents`; the
view-only path is covered by
`should_reject_drop_column_restrict_when_a_view_depends`. Both tests verify
non-mutation, and the foreign-key case verifies enforcement after rejection.
Broader #839 acceptance remains open.

### 2026-10-29 — #826 concurrent-refresh cancellation cleanup

`should_cleanup_unpublished_indexes_when_concurrent_refresh_is_cancelled_before_activation`
injects cancellation at the activation boundary after replacement output and
copied indexes have been built. It verifies the unpublished output and indexes
are removed, the candidate version is marked failed, the previous output stays
active, and a subsequent refresh succeeds. A second cancellation injected after
activation metadata preparation but before the final interruption check must
leave the prior output active. A cancellation after that check may race with
successful publication, consistent with the cooperative boundary used by
staged writes. An injected pre-publication activation failure exercises the
same cleanup, and a local-storage restart witness verifies the failed candidate
and prior active output recover before a later refresh succeeds. This closes
only the selected pre-activation cleanup gap; broader #826 table-creation and
materialized-view acceptance remains open.
