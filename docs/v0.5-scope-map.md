# v0.5.0 Authoritative Columnar Tables

The v0.5.0 feature scope (renumbered from v0.3.0 on 2026-11-12) is the per-table authoritative columnar storage
capability defined by issues [#1105–#1112](https://github.com/cntryl/cassie/milestone/10).
The current issue assignment and dependency order are recorded in
[Release Milestones](release-milestones.md). This replaces the former draft
v0.3 projection-store map; that pre-release history remains in
[v0.1.0 Issue-to-Contract Map](v0.1-scope-map.md).

The selected per-table contract is [Column-Authoritative Table Contract](columnar-table-contract.md)
(owner-approved SQL, format and conversion on 2026-11-13; #1105).

## #826 remaining forms (v0.5.0)

Issue [#826](https://github.com/cntryl/cassie/issues/826) moved its remaining
storage-metadata work to this milestone. Column `STORAGE` and `COMPRESSION`
are **catalog metadata only**: Cassie stores rows through Midge, so neither
setting changes physical layout or value encoding. They are recorded in the
column's `FieldConstraint` (`storage`, `compression`; absent means the type
default) and need no migration because old data deserializes with the defaults.

| Form | Status |
|------|--------|
| `col type STORAGE {PLAIN\|EXTERNAL\|EXTENDED\|MAIN\|DEFAULT}` and `COMPRESSION {pglz\|lz4\|default}` in `CREATE TABLE` / `ADD COLUMN` | Supported; reported by `pg_attribute.attstorage` / `attcompression` |
| `ALTER TABLE ... ALTER COLUMN ... SET STORAGE` / `SET COMPRESSION` | Supported (including `DEFAULT` to reset) |
| Non-`PLAIN` storage or any compression on a fixed-width type | Rejected with `42804` before publication, as in PostgreSQL |
| Unknown storage strategy or compression method | Rejected with `22023` before publication |
| `CREATE MATERIALIZED VIEW ... USING heap`, `ALTER MATERIALIZED VIEW ... SET ACCESS METHOD heap` | Supported; no-op, rows unchanged, `pg_class.relam = 2` |
| Materialized view `USING columnar` or any non-heap method | Rejected with `0A000`; nothing published (materialized views are heap-only per the columnar table contract) |
| `LIKE ... INCLUDING COMMENTS` | Supported for column comments (table comment is not copied, as in PostgreSQL) |
| `LIKE ... INCLUDING STORAGE` / `INCLUDING COMPRESSION` | Supported, independently |
| `LIKE ... INCLUDING GENERATED`, `INCLUDING STATISTICS` | Accepted no-ops: Cassie has no generated expression columns or extended statistics, so there is nothing to copy |
| `LIKE ... INCLUDING DEFAULTS` with `nextval(...)` / `SERIAL` defaults | Supported; the copy shares the source's sequence (not owned), as in PostgreSQL |
| `LIKE ... INCLUDING INDEXES` for full-text and time-series indexes | Supported with target-owned names |
| `LIKE ... INCLUDING INDEXES` for vector, hybrid and column indexes | Rejected with `0A000` before publication |
| `LIKE ... INCLUDING ALL` | Selects every option above |

Domain-typed columns report the `EXTENDED` default storage because the base type
is not resolved in the catalog view. Column comments are copied after the target
is published, so a failure of that final step reports an error with the target
already created.
