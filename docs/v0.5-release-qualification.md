## Diagnostics and operational limits

`pg_am` identifies columnar table access method OID 9301; heap remains 2. `pg_class.relam` reports the table authority. `pg_table_storage.storage_mode` distinguishes `row-store`, derived `column-indexed`, and authoritative `column-store`. Text EXPLAIN names `storage_mode=column-store`; structured EXPLAIN reports authority separately from the derived accelerator. The catalog diagnostic witnesses are in `tests/catalog_security/catalogs/columnar_catalog_identity.rs`.

Conversion retains OID, row identities, schema, constraints, grants and comments. It uses one Midge transaction bounded by configured transaction memory/spill limits; admission failure leaves the previous authority intact. A row table with a derived column index must drop that index before conversion to columnar. Same-mode conversion is a no-op. Columnar stores require layout `cassie-midge-layout-v4-0.5.0-columnar`; an unsupported binary refuses the layout rather than migrating it. Development stores have no promised migration. See [storage compatibility](storage-compatibility-transition.md), [snapshot/restore](snapshot-restore.md), and [performance/resource contracts](performance-contracts.md).

The approved #1105 layout uses compact per-field values and live-marker revisions. It does not add a Cassie segment/manifest/checksum/codec or compaction engine: Midge owns physical durability, compaction and recovery. The [#1107 selected-format disposition](https://github.com/cntryl/cassie/issues/1107#issuecomment-6877177841) records this mapping. Original #1107 planning references to segments, split/merge and codecs map to the selected field-key/live-marker format, its golden framing, schema/storage versions and atomic publication; they do not assert an absent second storage layer.

Corruption validation is scoped to the data a path visits. Point and derived access validate requested candidate rows and fetched fields; explicit complete-traversal owners verify field/live-marker coverage; conversion validates its complete source before publication. Bounded LIMIT/EXISTS and resumable portals validate visited rows. Blocking operators retain complete-source intent even when output has a limit; physical transport or result caps do not silently select the integrity policy. A selective index query is not a whole-table corruption audit. The explicit storage verifier supplies that audit.

The fixtures qualify the named finite behaviors. They do not establish production capacity, a universal cancellation latency, performance superiority, or compatibility with every PostgreSQL form. Approximate retrieval retains its existing declared recall and fallback contract. This work does not expand the product boundary or introduce another storage layer.

## Representative benchmark evidence

Row-only, column-only and mixed-mode workloads must record the exact source revision, row count, query/DML shape, storage mode, configuration, hardware and typed stress-runner results. Timing belongs in benchmarks; correctness tests contain no performance timing assertion. The typed `tier3_system_storage_modes` owner uses exactly 100,000 fact rows and 1,000 dimension rows, memory storage, 5,000-row untimed COPY setup batches, the explicit benchmark-only `storage_modes_100k_2g` 2 GiB per-query budget and disabled result caching. Ten fixed-duration scenarios cover heap/columnar full scans, narrow projection and filtered aggregation, then all four heap/columnar join input combinations. Independent deterministic expected relations are checked before timing; each timed operation includes a result fingerprint check, so reported latency includes SQL execution, result materialization and verification rather than executor-only time. The separate `column_validation_reads` diagnostic is adapter-wide and cumulative: it counts logical validation field entries plus marker lookup attempts, not physical I/O or per-query reads. Per-case benchmark deltas span `measure_batch`, including harness warmup; they supplement the unchanged source-row scan metrics and are reported with that scope. Actual run receipts are pending the coherent candidate. No benchmark pass or throughput claim is made yet.

## Defect review and closeout

The first integrated candidate `f3c29f45c60ab3ae9e194575cf9b0889b75a5501` (tree `4892c801a14151dacadaf35cd4c969ff5193087d`) passed the build, then its full locked test command stopped with 13,305 passed, three failed and nine ignored across completed targets. Later targets were not run. The three new HNSW/IVFFlat/hybrid restart fixtures attempted root-only vector extension installation through a tester session; the fixture now installs the extension through root before tester queries, without changing its retrieval/restart assertions; execution on the corrected candidate is pending. Clippy, formatting, policy validators and benchmarks did not run on that attempt. These are observed fixture failures, not observed RED evidence for the production fixes.

The initial review identified four findings grouped into three correction areas: orphan fields were omitted by complete scans; conversion could discard those orphan fields; reverse conversion undercounted decoded-value memory; and LIKE comment failures could leave a published clone. Focused probes were authored before fixes, with execution deferred to the bundle gate. A later review found that the initial orphan preflight did whole-table work before bounded LIMIT/EXISTS reads and hid the validation-read count. That finding superseded source acceptance even though the executed tests had not exposed it. The repair makes bounded versus complete traversal intent explicit, reports validation work separately, and adds tiny LIMIT/EXISTS, callback, full-cursor and portal witnesses. The corrected immutable input was source-reviewed; integrated review and the repeated complete gate remain pending.

The reviewer audits exact source and integrated diff identities using source-backed Jev questions and focused probes for probabilities at or above 0.30. Confirmed defects must be fixed and reviewed; a model result does not establish correctness. Final disposition records will name each finding, evidence and corrective witness.

Before closing #1113 or the milestone, verify the complete acceptance matrix, local gate, benchmark results, exact final-head hosted checks and review status. Read back the squash merge commit/tree and all ten issue states. Release publication and production readiness remain separate actions.
