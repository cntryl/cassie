## Diagnostics and operational limits

`pg_am` identifies columnar table access method OID 9301; heap remains 2. `pg_class.relam` reports the table authority. `should_report_column_storage_in_text_explain_for_a_column_table_only` executed `EXPLAIN SELECT` for both authorities and passed in the full gate. `pg_table_storage.storage_mode` distinguishes `row-store`, derived `column-indexed`, and authoritative `column-store`. Text EXPLAIN names `storage_mode=column-store`; structured EXPLAIN reports authority separately from the derived accelerator. The catalog diagnostic witnesses are in `tests/catalog_security/catalogs/columnar_catalog_identity.rs`.

Conversion retains OID, row identities, schema, constraints, grants and comments. It uses one Midge transaction bounded by configured transaction memory/spill limits; admission failure leaves the previous authority intact. A row table with a derived column index must drop that index before conversion to columnar. Same-mode conversion is a no-op. Columnar stores require layout `cassie-midge-layout-v4-0.5.0-columnar`; an unsupported binary refuses the layout rather than migrating it. Development stores have no promised migration. See [storage compatibility](storage-compatibility-transition.md), [snapshot/restore](snapshot-restore.md), and [performance/resource contracts](performance-contracts.md).

The approved #1105 layout uses compact per-field values and live-marker revisions. It does not add a Cassie segment/manifest/checksum/codec or compaction engine: Midge owns physical durability, compaction and recovery. The [#1107 selected-format disposition](https://github.com/cntryl/cassie/issues/1107#issuecomment-6877177841) records this mapping. Original #1107 planning references to segments, split/merge and codecs map to the selected field-key/live-marker format, its golden framing, schema/storage versions and atomic publication; they do not assert an absent second storage layer.

Corruption validation is scoped to the data a path visits. Point and derived access validate requested candidate rows and fetched fields; explicit complete-traversal owners verify field/live-marker coverage; conversion validates its complete source before publication. Bounded LIMIT/EXISTS and resumable portals validate visited rows. Blocking operators retain complete-source intent even when output has a limit; physical transport or result caps do not silently select the integrity policy. A selective index query is not a whole-table corruption audit. The explicit storage verifier supplies that audit.

The fixtures qualify the named finite behaviors. They do not establish production capacity, a universal cancellation latency, performance superiority, or compatibility with every PostgreSQL form. Approximate retrieval retains its existing declared recall and fallback contract. This work does not expand the product boundary or introduce another storage layer.

## Defect review and closeout

The audit corrected four initial findings grouped into three areas: complete scans omitted orphan fields; conversion could discard them; reverse conversion undercounted retained typed values; and LIKE comment failure could leave a published clone. Source-first probes were authored before implementation with execution deferred; no unobserved baseline failure is called RED. Review subsequently caught an introduced full-preflight regression for bounded LIMIT/EXISTS and hidden validation work. Explicit traversal intent, logical versus physical caps and separate validation counters repaired it; bounded, blocking, join, callback and portal witnesses passed.

The first full gate failed three new restart fixtures because tester sessions attempted root-only vector extension installation. The fixtures now install through root and retain the retrieval assertions. Later strict-lint and test-policy attempts exposed helper/state-shape, assertion, benchmark formatter and test-name defects. Each failed or canceled receipt remains separate; none is relabeled a pass. The final coherent production gate and affected benchmark checks above supersede their qualification status.

The first default-native capacity probe on `7efce8ef` found a known committed COPY batch reported as failed during statistics maintenance: authoritative rows and independent PK/value SHA-256 matched all 85,000 requested rows, while runtime epoch/catalog hints remained at 80,000. Actual native defaults were 12 GiB total with a 64 MiB memtable/flush threshold; this was native capacity, not SQL query admission. The corrected probe on `2c4fd9d5` acknowledged those 85,000 rows with runtime/native epochs 17/17 and no stale hint; the next 5,000-row batch failed before commit, leaving exactly the acknowledged prefix and matching hash. Both are diagnostic-only memory runs, not local-durability or warm-cache proofs. Four tiny COPY regressions passed in the full gate, including cache-enabled freshness, retired-owner protection and actual target-database-family flush routing. The [COPY contract](transaction-owned-copy-2026-11-06.md#acknowledged-copy-batches-and-ancillary-maintenance-v050) preserves mandatory durability barriers and unknown-outcome quarantine.

The global minimum-reader fence is a separate durable monotonic schema-family prerequisite; it can remain raised after an unsuccessful first column operation. SQL rows/catalog still publish atomically in their database family. Existing generic durable/monotonic fence and v4 ordering units passed; no separately named v4 failed-SQL-rollback test is invented. See the [approved clarification](https://github.com/cntryl/cassie/issues/1105#issuecomment-6878076513).

Exact input and integrated reviews identify base/head/tree identities. Source-backed Jev findings were traced and corrected; its probabilities do not prove correctness. The [#1113 closeout record](https://github.com/cntryl/cassie/issues/1113) owns actual final-head hosted checks, formal review-status readback, squash commit/tree and all ten issue/milestone states. Package publication, Linux disk capacity and production readiness are separate qualifications.
